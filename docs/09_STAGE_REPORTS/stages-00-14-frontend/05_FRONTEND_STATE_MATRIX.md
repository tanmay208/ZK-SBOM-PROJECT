# Frontend State Matrix

Date: 2026-09-25
This is a design inventory only. No states are implemented here.

## State Vocabulary

All feature consumers should account for: initial, loading, success, empty, validation error, unauthorized (401), forbidden (403), not found (404), conflict (409), rate limited (429), server error (5xx), network failure, timeout, retry, stale data, partial failure, processing, completed, failed, and revoked/unavailable where applicable.

## Error Presentation Rules

Use field-level messages only for validated, non-sensitive backend errors. Use generic messages for network/server/tool failures. Do not render raw `ProofJobResponse.error_message`, subprocess stderr, stack traces, filesystem paths, raw SBOM content, PURLs, or private witness data. Preserve request correlation information only if the backend defines a non-sensitive identifier.

## Polling and Staleness

Proof lifecycle polling interval, terminal statuses, retry budget, cancellation, and server rate limits are UNKNOWN. They must be defined in the API contract before implementation. Snapshot/proof/certificate status should show the server timestamp where available and clearly distinguish stale data from current success.

## Stage 1.5 Contract States

- 401 responses are structured as `UNAUTHORIZED`; the bearer session is expired/absent and the frontend must clear its in-memory token.
- 403 responses are structured as `FORBIDDEN`; the resource exists or the action is known but the role/ownership policy denies it.
- 404, 409, 413, 422, 429, 502, and 503 use stable error codes when emitted by the application. 429/502/503 are not currently generated by confirmed routes.
- 500 responses are `INTERNAL_ERROR` with no exception detail.
- Proof failures render a generic failure state; raw `error_message` diagnostics are not frontend-consumable.
- Snapshot list/detail states no longer include a provisional SMT root; the public root remains a future approved commitment field only when the backend contract explicitly freezes it.
