## ADR 1: Cryptographic Design — BN254 & Poseidon
- **Date:** 2026-10-10
- **Status:** **ACCEPTED**
- **Context**: Need an efficient, SNARK-friendly hashing algorithm for large Merkle tree commitments (SBOMs, vulnerability databases).
- **Decision**: Standardize on canonical 32-byte big-endian BN254 scalar field encodings, using the Poseidon sponge permutation ($t=3$ for 2-to-1 binary nodes; $t=2$ for leaf commitments).
- **Rationale**: Highly efficient inside Noir/Barretenberg arithmetic circuits while remaining collision-resistant.

## ADR 2: Circuit Topology — 32-Component Segmentation
- **Date:** 2026-10-10
- **Status:** **ACCEPTED**
- **Context**: Proving a 1024-component SBOM against a 256-depth vulnerability SMT is computationally massive and exceeds memory limits if performed in a single monolithic circuit.
- **Decision**: Decompose the proof into chunked sequential proofs. Each chunk processes 32 components. There is an `init` segment, multiple `mid` segments, and a `final` segment linked by intermediate state hashes.
- **Rationale**: Keeps individual circuit gates small, proving time manageable, and avoids out-of-memory (OOM) failures.

## ADR 3: Proof Body Sizing — Legacy ACIR (2144 Bytes)
- **Date:** 2026-10-11
- **Status:** **ACCEPTED**
- **Context**: B1 proof validation required deterministic struct offsets for UltraPlonk proofs generated by Noir 0.32.0.
- **Decision**: Enforce a strict 2144-byte proof body, tied specifically to `@noir-lang/backend_barretenberg@0.32.0`.
- **Rationale**: The official Barretenberg API requires distinct arrays for public inputs and the proof body.

## ADR 4: ZKP Container Memory Limits (8 GB)
- **Date:** 2026-10-11
- **Status:** **ACCEPTED**
- **Context**: Background proof generation for the 256-segment Golden Path was failing silently via SIGKILL.
- **Decision**: Raised Docker container memory limit from 4GB to 8GB (`docker-compose.yml`).
- **Rationale**: The Node.js proving process required up to ~6GB during recursive segment proving. 8GB stabilized the pipeline.

## ADR 5: Verification Result Strictness — Distinct Error Categories
- **Date:** 2026-10-11
- **Status:** **ACCEPTED**
- **Context**: Proof validation can fail at multiple lifecycle stages (malformed bytes, network errors, invalid witnesses, failed math).
- **Decision**: Never collapse result categories. `STRUCTURAL_REJECTION`, `RUNTIME_FAILURE`, and `ENVIRONMENT_FAILURE` must remain strictly distinct from `CRYPTOGRAPHIC_FALSE`.
- **Rationale**: Returning `false` implies the proof was well-formed but mathematically invalid. A malformed proof or crashed container is an operational error, not a cryptographic assertion. Only explicit Boolean `true` from the verifier API triggers certificate issuance.

## ADR 6: Dynamic Sparse Merkle Tree Depth Validation (`AUD-A-010`)
- **Date:** 2026-10-12
- **Status:** **ACCEPTED**
- **Context**: Module-level import-time evaluation of `DEV_MODE=1` pinned SMT empty hash tables to depth 3, causing `IndexError` when ProverService explicitly initialized depth 256.
- **Decision**: Precompute empty hashes dynamically per instance inside `SparseMerkleTree.__init__(depth)` and enforce depth bounds.
- **Rationale**: Decouples tree capacity from ambient environment flags while ensuring safe execution at any depth up to 256.

## ADR 7: Multi-Layer Tenant Isolation (`AUD-A-001`)
- **Date:** 2026-10-12
- **Status:** **ACCEPTED**
- **Context**: Unscoped `(name, vendor)` queries in `sbom_repository.py` could link an uploaded SBOM to an Application record owned by a different user.
- **Decision**: Enforce tenant scoping across three distinct layers:
  1. Service/Repository query filters include `user_id`.
  2. Database models define a `UniqueConstraint("name", "vendor", "user_id")`.
  3. Schema migration (`014`) creates the unique index in PostgreSQL.
- **Rationale**: Defense in depth prevents accidental cross-tenant data leakage.

## ADR 8: Separation of Duties for Vulnerability Data (`AUD-A-009`)
- **Date:** 2026-10-12
- **Status:** **ACCEPTED**
- **Context**: Allowing any administrative user or automated service to directly publish authoritative vulnerability roots creates supply chain tamper risks.
- **Decision**: Restrict vulnerability ingestion to the `trusted_importer` role, which creates snapshots in `pending` state. Restrict snapshot approval and freezing to the `admin` role. Mandate that verification queries match `status == "frozen"` and `authoritative_smt_root`.
- **Rationale**: Enforces organizational separation between data ingestion and authoritative verification baselines.

## ADR 9: Verification Subprocess Offloading (`AUD-A-005`)
- **Date:** 2026-10-12
- **Status:** **ACCEPTED**
- **Context**: Running 256 sequential Node.js verification subprocesses in FastAPI route handlers blocked the event loop for tens of seconds, causing HTTP timeouts.
- **Decision**: Offload synchronous multi-segment verification calls to Starlette's `run_in_threadpool`.
- **Rationale**: Prevents event-loop starvation and allows other concurrent requests to proceed smoothly.

## ADR 10: Online Symmetric Certificate Lifecycle (`AUD-A-006`)
- **Date:** 2026-10-12
- **Status:** **ACCEPTED**
- **Context**: Evaluated asymmetric (ECDSA/Ed25519) offline-verifiable certificates vs symmetric HS256 tokens.
- **Decision**: Standardize on symmetric HS256 certificates coupled with mandatory online database revocation checks (`revoked_at` query).
- **Rationale**: Fits the centralized supply chain verification portal architecture where certificates can be instantly revoked and checked against real-time database state. Offline asymmetric verification remains deferred.

## ADR 12: Dual Database Local Isolation Architecture
- **Date:** 2026-10-14
- **Status:** **ACCEPTED**
- **Context**: The existing PostgreSQL database on port 5432 (`ZKP_SBOM`) contains protected historical baseline data that must not be altered, but local testing requires a fully migrated (revision 014) database.
- **Decision**: Run a separate disposable PostgreSQL 16 container (`zkp_sbom_local_dev`) on loopback port `5433` (`ZKP_SBOM_LOCAL_DEV`) for all local testing, development, and migrations. Leave port 5432 completely untouched.
- **Rationale**: Complete isolation guarantees zero accidental modification of the protected database while allowing full local testing.

### Decision D5-OD1: Prover Testing (Separately Planned Live Proof Generation Gate)
- **Date:** 2026-10-19
- **Status:** **ACCEPTED / RATIFIED**
- **Context**: Offline mocked tests verify API wiring, schemas, and orchestration, but do not prove that local Barretenberg / Nargo binaries execute a full 256-segment UltraPlonk proof end-to-end.
- **Decision**: The owner requires live 256-segment proof generation to be included in the routine D5 regression gate. This requires a separately planned, resource-bounded live test with explicit execution authorization before running it. Offline mocked tests remain useful but do not substitute for the owner's live-test requirement.
- **Rationale**: Provides empirical zero-knowledge proof generation verification while managing long runtimes and memory constraints through explicit authorization gates.

### Decision D5-OD2: Administrator Proof-Job Visibility (`all_tenants=true`)
- **Date:** 2026-10-19
- **Status:** **ACCEPTED / RATIFIED**
- **Context**: Proof jobs are currently strictly filtered to `ProofJob.user_id == current_user.id`. Administrators need visibility into system-wide proof generation activity to monitor worker status and troubleshoot failures, matching the pattern established for SBOM listing in Stage D4.3.
- **Decision**: Approve an optional `all_tenants=true` parameter for proof-job listing (`GET /api/v1/zkp`), defaulting to `false` and restricted to active administrators. Non-admin users must remain user/tenant-scoped. The implementation must follow existing authorization conventions and must not expose private proof data.
- **Rationale**: Enables governance observability for administrators without weakening tenant isolation or exposing confidential component details.

### Decision D5-OD3: Sequential Stage D5 Unit Breakdown (D5.1–D5.4)
- **Date:** 2026-10-19
- **Status:** **ACCEPTED / RATIFIED**
- **Context**: Stage D5 encompasses complex worker subprocess management, advisory lock concurrency, archive packaging, and frontend tracking. Attempting monolithic execution introduces risk of large diffs and regressions.
- **Decision**: Approve four separate sequential units:
  - **D5.1**: Prover Worker Runtime & Resource Controls.
  - **D5.2**: Proof Job Lifecycle, Advisory Locks & Abandoned-Job Recovery.
  - **D5.3**: Proof Archive Assembly & Verification Handoff Integrity.
  - **D5.4**: Frontend Proof Tracking & Consolidated Acceptance Gate.
  Each unit requires separate explicit authorization and acceptance. Approval of this breakdown does not authorize implementation of any unit.
- **Rationale**: Ensures granular, reviewable progress with strict acceptance criteria per module.

## ADR 13: Vulnerability Snapshot Freshness & TTL Lifecycle (`Stage D7`)
- **Date:** 2026-10-22
- **Status:** **ACCEPTED / OWNER RATIFIED**
- **Context**: Authoritative vulnerability snapshots require time-bounded validity to prevent stale compliance claims while preserving backward compatibility and historical certificate validity.
- **Decision**: Implement seven locked architectural decisions (`D7-POL-01` through `D7-POL-07`):
  1. Default TTL is 30 days (`2,592,000` seconds); bounded between 1 hour (`3,600`s) and 365 days (`31,536,000`s) via `VULNERABILITY_SNAPSHOT_TTL_SECONDS`. Out-of-bounds configurations fail closed with `SnapshotTTLConfigurationError` (silent clamping prohibited).
  2. Expiration is calculated strictly from snapshot freezing (`frozen_at`), never intake or approval time.
  3. Nullable `expires_at` column added via forward-only migration `016_add_snapshot_ttl_expires_at.py`.
  4. Evaluated synchronously without background daemons at three required checkpoints: proof-job creation (`zkp_repository.py`), prover preflight (`prover_service.py`), and authoritative verification (`verification_repository.py`).
  5. Legacy snapshots with `expires_at = NULL` grandfathered as non-expired to ensure backward compatibility.
  6. Historical issued certificates remain valid and independently verifiable even after source snapshot expiry.
- **Rationale**: Balances real-time freshness enforcement with cryptographic reproducibility and legacy preservation.

## ADR 14: Fail-Closed Non-Proving Verification & Foreign-Key Resilience (`Stage D9`)
- **Date:** 2026-10-23
- **Status:** **ACCEPTED**
- **Context**: In end-to-end integration workflows, verification endpoints can be invoked with unproven or non-existent proof jobs. If `proof_job_id` is an SQL foreign key to `zkp.proof_jobs.id`, an unproven/non-existent ID causes an SQL ForeignKeyViolation (HTTP 500) rather than a graceful domain rejection.
- **Decision**: In `verification_service.py` and `verification_repository.py`, check whether the provided `proof_job_id` exists in `zkp.proof_jobs`. If absent, decouple raw input from the foreign-key column, safely recording `proof_job_id = None` on the `verification_requests` audit row. Return `verification_unavailable` with `certificate: null` (HTTP 200). Strictly prohibit certificate issuance without verified cryptographic proofs.
- **Rationale**: Preserves fail-closed verification semantics while preventing database 500 errors and ensuring clean audit logging.

## ADR 15: Canonical Project Context Architecture with Root Compatibility Mirrors
- **Date:** 2026-10-23
- **Status:** **ACCEPTED**
- **Context**: Duplicated documentation across `.agents/`, `.context/`, `project_context/`, and root markdown created confusion, while moving everything without compatibility pointers broke automated tools (`bootstrap.ps1`, IDE rules discovery).

  2. `.context/` (Current Working Context & Session Continuity)
  3. `project_context/` (Authoritative Technical Governance & Specifications)
  Maintain root-level compatibility mirrors (`.agents/rules/`, `.context/`, `project_context/`, `AGENTS.md`, `README.md`, `PROJECT_CONTEXT.md`) that point to or synchronize with the canonical context.
- **Rationale**: Provides a single source of truth for humans and AI agents while guaranteeing 100% backward compatibility for all existing scripts, IDE discovery, and toolchains.
