## 2. Mathematical Primitives & Field Representation

1. **Curve & Scalar Modulus**:
   - All arithmetic circuits and commitment hashes operate over the BN254 (alt_bn128) scalar field $\mathbb{F}_r$, where:
     $$r = 21888242871839275222246405745257275088548364400416034343698204186575808495617$$
2. **Canonical 32-Byte Big-Endian Encoding**:
   - Field elements must always be encoded as **canonical 32-byte big-endian byte sequences** or `0x`-prefixed 64-character hexadecimal strings.
   - Any value $x \ge r$, negative integer, or non-hexadecimal character must be rejected immediately (`LegacyAcirVerificationError`).

## 3. Hash Function Invariants (Poseidon Sponge)

1. **Parameters**:
   - Leaf commitments (1 input $\rightarrow$ 1 hash): Poseidon permutation with width $t=2$.
   - Internal binary Merkle nodes (2 inputs $\rightarrow$ 1 hash): Poseidon permutation with width $t=3$.
2. **Deterministic Precomputations**:
   - Empty node hashes must be precomputed deterministically for every level of the tree.
   - Never substitute SHA-256, Keccak, or standard Blake2 for Poseidon in circuit-verified Merkle trees.

---

## 4. Tree Topologies & Capacity Bounds

1. **SBOM Merkle Tree**:
   - **Topology**: Full binary Merkle tree of depth 10.
   - **Capacity**: Exactly $2^{10} = 1024$ component leaves.
   - **Padding**: If an SBOM contains fewer than 1024 components, remaining leaves are padded deterministically with zeros before computing the root.
2. **Vulnerability Sparse Merkle Tree (SMT)**:
   - **Topology**: Sparse Merkle Tree of depth 256.
   - **Dynamic Depth Safety (`AUD-A-010`)**: Empty hash precomputation must occur dynamically per tree instance (`SparseMerkleTree.__init__(depth)`). Never rely on ambient global flags or hardcoded tables.

## 5. Circuit Decomposition & Legacy ACIR Proof Layout

To prevent out-of-memory crashes on large SBOMs, the proof is decomposed into 32-component chunks linked sequentially:

```
[Chunk 0: segment_init_32] ──(hash_out)──> [Chunk 1..30: segment_mid_32] ──(hash_in)──> [Chunk 31: segment_final_32]
```

### 5.1 Public Input Vectors
The order and count of public inputs are strictly fixed by circuit schemas:

1. **`segment_init_32`** (5 public inputs, 160 bytes prefix, total complete proof: **2304 bytes**):
   ```
   [global_sbom_root, policy_hash, chunk_index, components_commit, hash_out_commit]
   ```
2. **`segment_mid_32`** (4 public inputs, 128 bytes prefix, total complete proof: **2272 bytes**):
   ```
   [segment_index, components_commit, hash_in_commit, hash_out_commit]
   ```
3. **`segment_final_32`** (3 public inputs, 96 bytes prefix, total complete proof: **2240 bytes**):
   ```
   [vulnerability_db_root, components_commit, hash_in_commit]
   ```

### 5.2 Legacy ACIR Body Offset
- The official UltraPlonk proof body generated by `@noir-lang/backend_barretenberg@0.32.0` is **strictly 2144 bytes**.
- The complete proof consists of:
  $$\text{CompleteProofSize} = (\text{PublicInputCount} \times 32) + 2144$$
- The adapter ([`legacy_acir.py`](file:///E:/Main%20Project/backend/verification_service/app/core/legacy_acir.py)) splits incoming proof artifacts into public inputs and the 2144-byte body before invocation.

## 6. Public Input Binding Rules

1. **Metadata Binding**:
   - Public inputs submitted for verification must bind strictly to authoritative, persisted database records (`segment.global_sbom_root`, `segment.policy_hash`, `segment.vulnerability_db_root`), **never** to arbitrary byte slices extracted from untrusted client payloads.
2. **Snapshot Status Prerequisite**:
   - The verifier must verify that the referenced vulnerability snapshot is in `frozen` status with an exact match on `authoritative_smt_root`. Proofs evaluated against unfrozen or revoked snapshots must fail closed with `authoritative_record_mismatch`.

---

## 7. Fail-Closed Verification Strictness

1. **Explicit Boolean Acceptance**:
   - Only an explicit Boolean `true` returned by `BarretenbergVerifier.verifyProof()` constitutes valid cryptographic acceptance.
   - Command-line `bb verify` process exit codes (0 vs 1) are **never** authoritative on their own.
2. **Distinct Error States**:
   The verification engine must distinguish and never collapse the following failure modes:
   - `STRUCTURAL_REJECTION`: Proof body length is invalid, field encoding is malformed, or hex strings are invalid.
   - `RUNTIME_FAILURE`: Node.js process crashed, OOM killer terminated the verifier, or IPC communication failed.
   - `ENVIRONMENT_FAILURE`: Pinned packages or toolchain binaries are missing.
   - `CRYPTOGRAPHIC_FALSE`: The proof was structurally well-formed, but mathematically invalid.
   - *A runtime exception is an operational failure, NEVER a cryptographic proof of falsity.*

---

## 8. Anti-Mocking & Transparent Test Accounting

1. **No Simulated Verification in Production**:
   - Never implement fallback paths that return `verified: true` when crypto tools fail.
   - Stubs are permitted only in isolated, unit-test harnesses (such as testing database concurrency without waiting for expensive SNARK math).
2. **Skipped Tests Are Not Passes (`F2-C-001`)**:
   - 24 native Barretenberg tests in `test_b1_live_crypto.py` require a native Linux `bb` binary. On Windows hosts where `bb` is unavailable, these tests are skipped.
   - **Mandatory Rule**: Never represent skipped cryptographic tests as passes. All reports and test summaries must state the exact count of skipped tests and the environmental reason.
