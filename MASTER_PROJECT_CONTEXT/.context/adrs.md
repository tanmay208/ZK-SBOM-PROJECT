# Architecture Decision Records (ADRs)

**Freshness Date:** 2026-10-12  
**Purpose:** Consolidate key architectural, cryptographic, security, and operational decisions established across project stages.

---

## ADR 1: Cryptographic Design (BN254 & Poseidon)
- **Context**: Need a SNARK-friendly hashing algorithm for large Merkle tree commitments (SBOMs, vulnerability databases).
- **Decision**: Standardize on canonical 32-byte big-endian BN254 scalar field encodings, using the Poseidon sponge permutation ($t=3$ for 2-to-1 binary nodes; $t=2$ for leaf commitments).
- **Rationale**: Highly efficient inside Noir/Barretenberg arithmetic circuits while remaining collision-resistant.

---

## ADR 2: Circuit Topology (32-Component Segmentation)
- **Context**: Proving a 1024-component SBOM against a 256-depth vulnerability SMT is computationally massive and exceeds memory limits if done in a single monolithic circuit.
- **Decision**: Decompose the proof into chunked sequential proofs. Each chunk processes 32 components. There is an `init` segment, multiple `mid` segments, and a `final` segment linked by intermediate state hashes.
- **Rationale**: Keeps individual circuit gates small, proving time manageable, and avoids out-of-memory (OOM) failures.

---

## ADR 3: Proof Body Sizing (Legacy ACIR)
- **Context**: B1 proof validation needed deterministic struct offsets for UltraPlonk proofs generated by Noir 0.32.0.
- **Decision**: Enforce a strict 2144-byte proof body, tied specifically to `@noir-lang/backend_barretenberg@0.32.0`.
- **Rationale**: The official Barretenberg API requires distinct arrays for public inputs and the proof body.

---

## ADR 4: ZKP Container Memory Limits
- **Context**: Background proof generation for the 256-segment Golden Path was failing silently via SIGKILL.
- **Decision**: Raised Docker container memory limit from 4GB to 8GB (`docker-compose.yml`).
- **Rationale**: The Node.js proving process required up to ~6GB during recursive segment proving. 8GB stabilized the pipeline.

---

## ADR 5: Verification Result Strictness
- **Context**: Proof validation can fail at multiple lifecycle stages (malformed bytes, network errors, invalid witnesses, failed math).
- **Decision**: Never collapse result categories. `STRUCTURAL_REJECTION`, `RUNTIME_FAILURE`, and `ENVIRONMENT_FAILURE` must remain strictly distinct from `CRYPTOGRAPHIC_FALSE`.
- **Rationale**: Returning `false` implies the proof was perfectly well-formed but mathematically invalid. A malformed proof or crashed container is an operational error, not a cryptographic assertion. Only explicit Boolean `true` from the verifier API triggers certificate issuance.

## ADR 6: Dynamic Sparse Merkle Tree Depth Validation (AUD-A-010)
- **Context**: Module-level import-time evaluation of `DEV_MODE=1` pinned SMT empty hash tables to depth 3, causing `IndexError` when ProverService explicitly initialized depth 256.
- **Decision**: Precompute empty hashes dynamically per instance inside `SparseMerkleTree.__init__(depth)` and enforce depth bounds.
- **Rationale**: Decouples tree capacity from ambient environment flags while ensuring safe execution at any depth up to 256.

---

## ADR 7: Multi-Layer Tenant Isolation (AUD-A-001)
- **Context**: Unscoped `(name, vendor)` queries in `sbom_repository.py` could link an uploaded SBOM to an Application record owned by a different user.
- **Decision**: Enforce tenant scoping across three distinct layers:
  1. Service/Repository query filters include `user_id`.
  2. Database models define a `UniqueConstraint("name", "vendor", "user_id")`.
  3. Schema migration (`014`) creates the unique index in PostgreSQL.
- **Rationale**: Defense in depth prevents accidental cross-tenant data leakage.

---

## ADR 8: Separation of Duties for Vulnerability Data (AUD-A-009)
- **Context**: Allowing any administrative user or automated service to directly publish authoritative vulnerability roots creates supply chain tamper risks.
- **Decision**: Restrict vulnerability ingestion to the `trusted_importer` role, which creates snapshots in `pending` state. Restrict snapshot approval and freezing to the `admin` role. Mandate that verification queries match `status == "frozen"` and `authoritative_smt_root`.
- **Rationale**: Enforces organizational separation between data ingestion and authoritative verification baselines.

---

## ADR 9: Verification Subprocess Offloading (AUD-A-005)
- **Context**: Running 256 sequential Node.js verification subprocesses in FastAPI route handlers blocked the event loop for tens of seconds, causing HTTP timeouts.
- **Decision**: Offload the synchronous multi-segment verification calls to Starlette's `run_in_threadpool`.
- **Rationale**: Prevents event-loop starvation and allows other concurrent requests to proceed smoothly.

---

## ADR 10: Online Symmetric Certificate Lifecycle (AUD-A-006)
- **Context**: Evaluated asymmetric (ECDSA/Ed25519) offline-verifiable certificates vs symmetric HS256 tokens.
- **Decision**: Standardize on symmetric HS256 certificates coupled with mandatory online database revocation checks (`revoked_at` query).
- **Rationale**: Fits the centralized supply chain verification portal architecture where certificates can be instantly revoked and checked against real-time database state. Offline asymmetric verification remains deferred.
